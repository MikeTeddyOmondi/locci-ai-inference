## Tenant header and spoofing

KrakenD 2.13 only forwards a `propagate_claims` header when that header is also listed in `input_headers`. Without it, the router sees no tenant and answers 401. Listing it would normally let clients send their own value, but the validator overwrites it with the claim. This was verified: a valid token plus `X-Locci-Tenant: evil-tenant` was metered under the token's user id, and the same header without a token got 401 at the edge.

Remaining gap: if a valid token lacks `properties.id`, nothing overwrites the header and a client-supplied value would pass through. Every locci-auth user token carries `properties.id` today. Keep it that way, or have KrakenD strip the header first.

- [ ] Strip `X-Locci-Tenant` at KrakenD before claim propagation, so a token without `properties.id` cannot pass a client-supplied tenant through.

## Resumable chat streams

Refreshing the web chat mid-reply loses the reply and the question just sent: the browser saves to IndexedDB only when a reply finishes, and the API's stream lives only as long as its HTTP response. The AI SDK has the client half (`chat.resumeStream()` calls `GET /api/chat/<id>/stream`, 204 when there is nothing to resume); the API records the UI message stream as it is sent and replays it. One interface (`examples/api/src/resumable/`), two stores, picked by `RESUMABLE_STREAMS=memory|ursula|off`. `off` keeps today's behaviour exactly, and requests without a `threadId` (CLI, temporary chats) are never recorded. Both stores, request ids and idempotency are done (see CHANGELOG.md and the examples README). What is left:

- [ ] Memory store: lost on API restart, and only works with one API instance.
- [ ] Stop only reaches the instance doing the generation (abort handles are local). With several instances behind Ursula, a stop marker in the stream would fix it.
- [ ] Ursula streams never expire, and the Ursula gateway has no DELETE, so every turn's reply stays. Add retention (Ursula-side or a gateway route) before real traffic.
- [ ] Tenant scoping lives in this repo's KrakenD only. The production Ursula gateway (events.locci.cloud, from docker-compose-templates/ursula) forwards `/{bucket}/{stream}` as-is, so any valid Locci token used directly there can read `chats/<sub>--<thread>` given both ids (thread ids are random UUIDs). Fix in the template next: `/chats/{stream}` routes that rewrite to `/chats/{JWT.sub}--{stream}`, after checking that the static route wins over `/{bucket}` and that KrakenD 2.7 substitutes `{JWT.sub}`; this repo's routes then drop their own prefix.
- [x] End-user sign-in behind `AUTH=locci|off`: the web app signs in through locci-auth (PKCE, one button, locci-auth's own sign-in page), the API verifies the bearer token, keeps threads and recordings per user, and sends the user's token to Ursula. See the examples README.
- [x] `/chat` (the CLI protocol) needs a bearer with `AUTH=locci`; the CLI and TUI send `LOCCI_ACCESS_TOKEN`, an exchanged `LOCCI_API_KEY`, or the session from `locci-chat login` (browser PKCE login, refreshed per request).
- [x] Sign-in clicked through in Chrome against local locci-auth: one button to locci-auth's own page (password and GitHub offered there), redirect back, refresh token stored, a bearer on every `/api` call, signed in after a reload, threads stored with the user as owner, Sign out back to the sign-in screen with the token cleared, no console errors.
- [ ] Resume after a reload with a signed-in user is checked by `examples-check` (key token) but not yet in the browser with a reply that finishes: during the browser runs the qwen3 node (`llama-coder-1`) kept restarting mid-reply (8 restarts, exit 0, no error logged), so the replies died upstream.
- [ ] The search planning step before the first chunk is not replayed (there is nothing to show yet).
- [ ] KrakenD CE (2.13) held a streamed GET from Ursula until about 4 KB had built up, so the Ursula store reads with long-polls. Anything else that needs live SSE through KrakenD should be measured first; the chat endpoint is fine because a reply crosses 4 KB quickly, but its first tokens arrive in batches.

## CLI agent: shell commands, resume, compaction

Next up: the CLI as a coding agent in whatever folder `locci-chat` is started from (a released CLI on the PATH, e.g. `~/src/mt0/test-project`), not the folder it is installed in.

- [ ] **Client-side `shell` tool (start here).** Defined in `examples/api/src/tools.ts` next to `weather` and `search`, but with no `execute`: the AI SDK then ends the step with the call (`finishReason: 'tool-calls'`) and the client runs it. `/chat` adds it only when the request says the client can run it (`clientTools: ['shell']`), so the web app and other callers never get it, and emits `{t:'tool-call', id, name, input}`. The CLI shows the command, asks `Run in <cwd>? [y/N/always]` (`--yes` skips it), runs it with `child_process` in `process.cwd()` with a timeout and an output cap, and posts `/chat` again with the assistant's tool call and a `tool` result (a refusal is a result, "the user declined", not an error), looping up to the API's 5 steps. Needs the CLI and TUI to keep AI SDK `ModelMessage`s instead of `{role, content: string}` pairs. The API never runs the command; an MCP server in the API's `mcp.json` can't reach the CLI's folder once the API is deployed, and a host-side shell tool would hand every signed-in user (or a page read during a search) a shell on the API server.
- [ ] `read_file` and `write_file` client tools the same way, rooted at the CLI's folder (paths outside it refused), once `shell` works.
- [ ] **Web chat backend for `shell`:** the same tool from the web app runs in a Locci Box agent box (server-side, isolated), not on any host; see the Locci Box item below. Until that exists, web chats don't get the tool.
- [ ] **Locci Box agent boxes** (locci-box repo, branch `feat/agent-boxes` from `feat/juicefs-persistent-volumes`, which is 20 commits ahead of `main` and not merged yet): a box that lives across calls (`box_create`, `box_exec` in `/workspace`, `box_write_file`, `box_read_file`, `box_stop`, an idle timeout, counted against the tenant's sandbox limit), an image with apt, git, curl and build tools, 1 to 2 GB and per-command timeouts in minutes, and open egress with private, link-local, CGNAT and loopback ranges (cloud metadata included) blocked, so the AI can install anything without reaching the host's network. Today's `run_sandbox` boots a microVM per snippet with 128 MB, a 30 s timeout and egress limited to PyPI, npm and Alpine. Ports exposed through a preview URL (`box_expose`) later, separately.
- [ ] **Resume CLI chats: `--continue` and `--resume <thread id>`.** CLI chats saved as threads through the API's thread store with the login's token (owner-scoped, so they also show in the web app). `--continue` picks up the latest thread started in this folder (the thread records its `cwd`), `--resume <uuid>` any of the user's threads, with the old messages printed. A thread also records its Locci Box id: resuming reattaches to the box, or, if it was stopped after idling, starts a new one on the same persistent `/workspace` (JuiceFS), so installed packages and files carry over.
- [ ] **Conversation compaction**, as current coding harnesses do, to replace today's lossy `fitToContext` (which drops the oldest turns outright). When a conversation passes about 75% of the model's window (or on `/compact` in the CLI), older turns are summarised by the model into a structured note (the goal, decisions and why, files touched, commands run and their outcomes, errors hit, open TODOs, facts the user gave), and the summary plus the latest few turns verbatim go to the model from then on. Cheapest losses first: long tool outputs and command logs are trimmed to their head, tail and exit code before any turn is summarised; summaries are compacted again when they grow. Stored with the thread (the summary and the index it covers) so a resume doesn't redo it, and the full history stays in the thread for the UI. Measure on the small models: a 1.7B model's summaries need checking that facts survive (a planted fact must still be answerable after compaction).
